# Правила разработки Bakunity Infra

Bakunity Infra использует Project Context System (PCS). Любые изменения должны сохранять не только кодовую/архитектурную целостность, но и актуальность переносимого project context.

Перед началом работы AI или разработчик должен выполнить bootstrap из `AGENTS.md`.

## Перед реализацией

Перед добавлением крупной возможности нужно определить:

1. Какому бизнес-модулю она принадлежит.
2. Относится ли она к текущему этапу roadmap.
3. Могут ли Web и Telegram использовать одну и ту же бизнес-логику.
4. Какие внешние адаптеры потребуются.
5. Какие правила авторизации должны применяться.
6. Какое событие аудита должно создаваться при изменении инфраструктуры.
7. Появляются ли новые секреты или привилегированные учётные данные.
8. Меняет ли работа semantic project state и какие PCS-документы потребуется обновить.

## PCS workflow

### Перед работой

Прочитать минимум:

```text
AGENTS.md
.project/state.json
docs/PROJECT_STATE.md
docs/ARCHITECTURE.md
docs/ACTIVE_WORK.md
```

Затем — только релевантные ADR и профильную документацию.

### Во время работы

- Не использовать chat memory как единственный источник project-specific truth.
- Работать относительно понятного base commit.
- Если repository state противоречит чату — сначала разобраться в drift.
- Не записывать предположение в `EVIDENCE.md` как факт.

### При semantic state transition

Проверить и при необходимости обновить:

```text
docs/PROJECT_STATE.md
docs/ACTIVE_WORK.md
docs/EVIDENCE.md
.project/state.json
```

Плюс соответствующий authoritative документ или новый ADR.

### После работы

`Done` допускается только если понятно:

- что изменено;
- на каком commit;
- что проверено;
- где evidence;
- обновлён ли context;
- какой следующий шаг.

## Архитектурные правила

- Сохранять проект модульным монолитом, пока нет документированной причины выделять отдельный сервис.
- Не размещать бизнес-логику в Telegram handlers или веб-компонентах.
- Не обращаться к инфраструктурным провайдерам напрямую из UI/client layer.
- Держать внешние системы за интерфейсами и адаптерами.
- Сохранять явные границы модулей.
- Не создавать общий shared-код без реальной и стабильной потребности.
- Предпочитать явные use case скрытым побочным эффектам между модулями.

## Web и Telegram

Веб-панель и Telegram-бот являются клиентами одной системы.

Одна бизнес-функция не должна иметь две независимые реализации одного и того же правила.

Пример:

```text
Web ───────┐
           ├── use case CreateSubdomain ──> модули Domains / DNS
Telegram ──┘
```

## Правила безопасности

Никогда не коммитить реальные учётные данные, токены, приватные ключи или production-файлы окружения.

Если изменение требует нового секрета, в документации указывается только название переменной/параметра и его назначение.

Операции, изменяющие инфраструктуру, должны с самого начала учитывать авторизацию и аудит.

## Размер изменений

Предпочтительны небольшие и понятные изменения.

Один pull request по возможности должен решать одну архитектурную или продуктовую задачу, а не одновременно объединять несвязанные рефакторинги, инфраструктурные изменения и новые функции.

## Документация

Authoritative карта находится в `AGENTS.md` и `docs/CONTEXT_SYSTEM.md`.

Типичные документы:

- продукт/границы — `docs/PRODUCT.md`, `docs/GOALS.md`;
- архитектура — `docs/ARCHITECTURE.md`;
- причины решений — `docs/ADR/`;
- roadmap/backlog — `docs/ROADMAP.md`, `docs/BACKLOG_V1.md`;
- текущее состояние — `docs/PROJECT_STATE.md`;
- активная работа — `docs/ACTIVE_WORK.md`;
- подтверждённые проверки — `docs/EVIDENCE.md`;
- безопасность — `docs/SECURITY.md`.

Нельзя создавать второй source of truth вместо обновления authoritative файла.

## Context validation

Локально:

```bash
python scripts/validate_context.py .
```

Validator проверяет структуру PCS и machine state. Он не заменяет смысловую архитектурную ревизию.

## Текущий статус

Точное состояние проекта берётся из `docs/PROJECT_STATE.md`, а не из этого файла. `CONTRIBUTING.md` описывает процесс и не должен дублировать текущий project state.
