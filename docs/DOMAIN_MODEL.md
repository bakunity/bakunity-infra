# Модель предметной области

Этот документ описывает основные сущности Bakunity Infra и отношения между ними до начала реализации. Это логическая модель продукта, а не схема конкретной базы данных.

## Общая схема

```text
Пользователь
   │
   ├── Идентичности (Web / Telegram)
   ├── Роли и права
   │
   └── владеет ресурсами
          │
          ├── Поддомены
          │     ├── DNS-записи
          │     ├── DNS-зона
          │     └── Привязка к серверу
          │
          └── Серверы (если разрешено политикой доступа)

DNS-провайдер
   └── DNS-зоны
          └── Поддомены / DNS-записи

Аудит
   └── фиксирует значимые действия над ресурсами
```

## Пользователь

**User** — внутренняя учётная сущность Bakunity Infra.

Пользователь не должен зависеть от конкретного клиента. Один и тот же пользователь может входить через Web и работать через Telegram.

Основные свойства:

- внутренний ID;
- отображаемое имя;
- статус: active / blocked / disabled;
- дата создания;
- роли;
- лимиты;
- связанные идентичности.

## Идентичность

**Identity** связывает внутреннего пользователя с внешним способом входа.

Примеры:

```text
User #1
├── Telegram identity: telegram_id=...
└── Web identity: login/email/SSO identity
```

Бизнес-логика должна работать с `User`, а не непосредственно с `telegram_id` или web-session.

## Роль и право

**Role** — набор разрешений.

**Permission** — конкретное действие, например:

- `domains.read`;
- `domains.create`;
- `domains.delete`;
- `dns.records.write`;
- `servers.manage`;
- `users.manage`;
- `audit.read`.

Права и модель владения описаны подробнее в [PERMISSIONS.md](PERMISSIONS.md).

## DNS-провайдер

**DNS Provider** — внешний backend для DNS.

На первом этапе — Cloudflare.

Провайдер не является источником истины для продукта. Bakunity Infra хранит собственное состояние и использует провайдера через адаптер.

## DNS-зона

**DNS Zone** — управляемая доменная зона, например:

```text
bakunity.online
bakunity.store
example.net
```

Основные свойства:

- внутренний ID;
- доменное имя;
- провайдер;
- внешний `zone_id` у провайдера;
- статус;
- доступность для пользователей;
- настройки лимитов и выдачи поддоменов.

Зона принадлежит системе или администратору, а не обычному пользователю.

## Поддомен / управляемый доменный ресурс

**Domain Resource** — домен или поддомен, которым Bakunity Infra управляет как отдельным ресурсом.

Пример:

```text
panel.bakunity.online
vpn.bakunity.online
api.bakunity.online
```

Основные свойства:

- имя (`panel`);
- полное имя (`panel.bakunity.online`);
- DNS-зона;
- владелец;
- статус;
- дата создания;
- лимит записей;
- опциональная привязка к серверу.

### Инварианты

- полное доменное имя должно быть уникально внутри системы;
- имя должно проходить DNS-валидацию;
- запрещённые и системные имена резервируются;
- пользователь не может создать ресурс в зоне, к которой у него нет доступа;
- удаление ресурса требует проверки зависимостей и прав.

## DNS-запись

**DNS Record** — запись, связанная с управляемой зоной или доменным ресурсом.

Для первой версии поддерживаются:

- A;
- AAAA;
- CNAME;
- TXT;
- MX;
- NS.

Основные свойства:

- тип;
- имя;
- значение;
- TTL;
- provider record ID;
- статус синхронизации;
- владелец через доменный ресурс;
- дополнительные типоспецифичные параметры, например priority для MX.

### Важный принцип

Сначала изменение проходит правила Bakunity Infra, затем DNS-модуль вызывает адаптер провайдера. Telegram и Web не работают с Cloudflare напрямую.

## Сервер

**Server** — зарегистрированный узел инфраструктуры.

На раннем этапе это каталог и метаданные, а не полноценное удалённое управление.

Основные свойства:

- имя;
- IPv4;
- IPv6;
- окружение: production / staging / development;
- провайдер или площадка;
- регион;
- статус;
- метки;
- владелец или область доступа.

Позже сервер может получить управляемые возможности через отдельные адаптеры SSH/agent/container runtime.

## Привязка домена к серверу

**Domain Binding** описывает намерение направить доменный ресурс на определённый сервер.

Для первой версии это связь уровня control plane:

```text
panel.bakunity.online
        │
        ▼
      Hermes
        │
        ▼
   31.x.x.x
```

Привязка не означает, что Bakunity Infra уже настраивает reverse proxy или приложение на сервере.

Позже эта сущность может расшириться полями:

- target port;
- protocol;
- reverse proxy route;
- TLS policy;
- deployment.

## Аудит

**Audit Event** — неизменяемая запись о значимом действии.

Примеры:

- создан поддомен;
- изменена DNS-запись;
- удалён ресурс;
- добавлен сервер;
- изменены права;
- выполнено действие через Telegram или Web.

Событие должно содержать:

- actor/user;
- source client;
- action;
- resource type;
- resource ID;
- результат;
- timestamp;
- безопасные метаданные без секретов.

## Будущие сущности

Не являются обязательными для первой версии, но архитектура должна позволять добавить:

- Deployment;
- Proxy Route;
- Certificate;
- Health Check;
- Incident;
- Notification;
- Secret Reference;
- Server Agent;
- Environment.

## Граница первой версии

Первая версия предметной модели должна уверенно покрывать:

```text
User
Identity
Role / Permission
DNS Provider
DNS Zone
Domain Resource
DNS Record
Server
Domain Binding
Audit Event
```

Остальные сущности добавляются только когда соответствующий этап roadmap переходит в разработку.
