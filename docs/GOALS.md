# Цели и стратегический вектор Bakunity Infra

Этот документ фиксирует, **зачем существует Bakunity Infra, какой результат мы строим и какие решения считаются правильным направлением**. Он нужен, чтобы проект не превращался в набор случайных функций по мере разработки.

# Миссия

Bakunity Infra должна стать единым control plane для повседневного управления доменами, DNS и связанной серверной инфраструктурой через два удобных клиента:

- Web Console;
- Telegram Bot.

Пользователь не должен каждый раз вручную открывать панели DNS-провайдеров, вспоминать IP серверов, редактировать конфиги и держать состояние инфраструктуры в голове.

# North Star-сценарий

Главный сценарий, вокруг которого строится первая версия:

```text
Выбрать DNS-зону
      ↓
Ввести поддомен
      ↓
Выбрать сервер / IPv4 / CNAME
      ↓
Подтвердить
      ↓
Bakunity Infra применяет DNS
      ↓
Ресурс виден в Web и Telegram
      ↓
Действие записано в аудит
```

Цель UX: типовое создание поддомена должно занимать **до одной минуты и несколько понятных действий**, если все необходимые серверы и зоны уже зарегистрированы.

# Долгосрочный вектор

Развитие продукта идёт по цепочке:

```text
Домены и DNS
      ↓
Каталог серверов и привязки
      ↓
Маршрутизация / reverse proxy
      ↓
TLS / HTTPS
      ↓
Деплои приложений
      ↓
Мониторинг и эксплуатация
      ↓
Полноценный infrastructure control plane
```

Каждый следующий слой строится поверх уже стабильного предыдущего слоя. Мы не начинаем автоматический деплой, пока система не умеет безопасно управлять ресурсами, правами, аудитом и состоянием DNS.

# Стратегические цели

## G1 — Единый источник истины

Bakunity Infra хранит собственную модель инфраструктуры в PostgreSQL.

Cloudflare и будущие внешние системы являются исполнителями и источниками внешнего состояния, но не заменяют внутреннюю модель продукта.

Web и Telegram должны показывать одно и то же состояние.

## G2 — Два клиента, одно ядро

Web Console и Telegram Bot — равноправные клиенты одной application layer.

Нельзя иметь отдельные DNS-правила, права доступа или жизненный цикл ресурсов для Telegram и Web.

Telegram может получать UX раньше, потому что быстрее разрабатывается, но backend use case создаётся один раз.

## G3 — Простое управление несколькими доменными зонами

Система должна изначально поддерживать несколько управляемых DNS-зон.

Примеры:

```text
bakunity.online
bakunity.store
другие подключённые зоны
```

Пользователь работает с зонами через Bakunity Infra, а не напрямую с provider-specific идентификаторами.

## G4 — Provider-neutral DNS

Cloudflare — первый DNS adapter, а не часть доменной модели.

Добавление второго DNS-провайдера в будущем не должно требовать переписывания Web, Telegram и основных use case.

## G5 — Безопасные инфраструктурные mutation

С первой версии должны существовать:

- authentication;
- authorization;
- ownership;
- audit log;
- явное подтверждение destructive actions;
- стабильные error codes;
- идемпотентность там, где повтор запроса может создать дубликат;
- защита от конфликтующих изменений Web/Telegram.

Без этого проект не переходит к SSH, reverse proxy и deployment automation.

## G6 — Сервер как управляемая цель, но не как удалённая shell-машина

В V1 Server — это ресурс каталога:

- имя;
- IPv4/IPv6;
- окружение;
- provider/region;
- labels;
- состояние регистрации;
- доступность для использования как target.

V1 умеет связать домен с сервером и создать соответствующий DNS target.

V1 **не** выполняет произвольные SSH-команды и не обещает мониторинг ОС.

## G7 — Расширение без переделки ядра

Архитектура должна позволить позже добавить:

- reverse proxy;
- TLS;
- deployment;
- monitoring;
- server agents;
- дополнительные DNS providers;
- CLI и внешние API clients.

Для этого сохраняются границы модульного монолита и ports/adapters на внешних интеграциях.

# Цель релиза V1

**V1 = безопасное управление доменами и DNS с минимальным каталогом серверов через Web и Telegram.**

V1 считается функционально состоявшейся, когда доступны:

1. несколько DNS-зон;
2. Cloudflare adapter;
3. создание и удаление управляемого поддомена;
4. A, AAAA, CNAME, TXT, MX, NS;
5. редактирование DNS-записей;
6. каталог серверов;
7. привязка поддомена к серверу;
8. роли, permissions, ownership и лимиты;
9. audit log для значимых mutation;
10. Telegram flow для основных операций;
11. Web flow для тех же операций;
12. нормализованные provider errors и sync status;
13. отсутствие production secrets в Git;
14. документация API и ключевых правил соответствует реализации.

# Критерии качества V1

V1 должна быть не просто демонстрацией UI.

Минимальные критерии:

- одна бизнес-операция имеет одинаковый результат из Web и Telegram;
- нельзя изменить чужой ресурс без соответствующего permission;
- повторный запрос не должен случайно создавать дубликаты там, где предусмотрена идемпотентность;
- ошибка Cloudflare не должна превращать внутреннее состояние в ложное `success`;
- каждый значимый mutation имеет audit event;
- destructive operation требует явного подтверждения в UI;
- доменные и серверные ресурсы имеют однозначные внутренние ID;
- секреты не попадают в API responses, Telegram, Web и audit metadata;
- пользователь может понять состояние ресурса без входа в Cloudflare.

# Что V1 намеренно не делает

Чтобы сохранить фокус, в V1 не входят:

- собственный authoritative DNS-сервер;
- произвольное выполнение shell-команд на серверах;
- автоматическая установка ПО на VPS;
- reverse proxy configuration;
- автоматический TLS/ACME;
- деплой приложений;
- Docker orchestration;
- полноценный мониторинг uptime/CPU/RAM;
- Kubernetes;
- multi-region orchestration;
- микросервисы ради архитектурной моды.

# Что идёт сразу после V1

Следующий продуктовый рубеж — **Managed Delivery**:

```text
Domain
  +
Server
  +
Target Port
   ↓
Reverse Proxy
   ↓
TLS
   ↓
Health Check
```

Только после стабильного Managed Delivery имеет смысл делать полноценные deployments.

# Правило приоритизации

При выборе между двумя задачами выше приоритет получает та, которая сильнее улучшает одно из четырёх направлений:

```text
1. Надёжность состояния
2. Безопасность изменений
3. Простота типовой операции
4. Расширяемость без дублирования логики
```

Функция, которая выглядит эффектно, но не помогает этим направлениям и не входит в текущий этап roadmap, откладывается.

# Антицели

Bakunity Infra не должна превращаться в:

- копию Cloudflare Dashboard;
- огромный Telegram-бот со всей логикой внутри handlers;
- универсальный SSH-terminal через Telegram;
- набор микросервисов без причины;
- dashboard, который показывает красивые графики, но не управляет реальным состоянием;
- систему, где Web, Telegram и provider показывают три разных версии правды.

# Формула продукта

Коротко направление можно зафиксировать так:

> **Bakunity Infra — единый, безопасный и удобный control plane для доменов и серверной инфраструктуры, доступный через Web и Telegram, который постепенно развивается от DNS-управления к доставке и эксплуатации приложений.**
