# Telegram UX

Telegram-бот — быстрый операционный клиент Bakunity Infra. Его задача — позволить выполнить типовые действия за несколько шагов, не превращая Telegram в копию полноценной веб-панели.

## Принцип

Telegram не содержит собственной бизнес-логики DNS или серверов.

```text
Telegram UI
    │
    ▼
Application use case
    │
    ▼
Domains / DNS / Servers
```

Если тот же сценарий существует в Web, итоговое состояние системы должно быть одинаковым.

## Главное меню

Для обычного пользователя:

```text
🌐 Bakunity Infra

Управление доменами и инфраструктурой.

[ 🌐 Получить поддомен ]
[ 📂 Мои домены ]
[ 🖥 Серверы ]
[ ℹ️ Информация ]
```

Для пользователя с административными правами дополнительно:

```text
[ ⚙️ Управление ]
```

Административные возможности нельзя показывать только на основании Telegram username — права проверяются backend.

# Сценарий: получить поддомен

## Шаг 1 — выбор зоны

```text
🌐 Получить поддомен

Выберите доменную зону:

[ bakunity.online ]
[ bakunity.store  ]
[ example.net     ]

[ ← Назад ]
```

Показываются только доступные пользователю зоны.

## Шаг 2 — имя

```text
Введите имя поддомена для bakunity.online

Например:
panel
vpn
api
```

После ввода бот валидирует:

- допустимые символы;
- длину;
- занятость;
- reserved names;
- пользовательский лимит.

## Шаг 3 — куда направить

```text
🌐 panel.bakunity.online

Куда направить поддомен?

[ 🖥 Выбрать сервер ]
[ ✏️ Ввести IPv4 ]
[ 🔗 CNAME ]

[ ← Назад ]
```

В будущих версиях могут появиться дополнительные варианты, но первая версия не должна перегружать этот экран.

## Шаг 4A — сервер

```text
Выберите сервер:

[ 🟢 Hermes ]
[ 🟢 Node-02 ]
[ 🟡 Staging ]

[ ← Назад ]
```

Показываются только разрешённые серверы.

## Шаг 4B — IP

Бот просит IPv4 и проверяет формат.

## Шаг 4C — CNAME

Бот просит hostname назначения и проверяет формат.

## Шаг 5 — подтверждение

```text
Проверьте настройки:

Домен: panel.bakunity.online
Назначение: Hermes
IPv4: 203.0.113.20

[ ✅ Создать ]
[ ✏️ Изменить ]
[ ❌ Отмена ]
```

Создание происходит только после подтверждения.

## Результат

```text
✅ Поддомен создан

🌐 panel.bakunity.online
🖥 Hermes
📍 203.0.113.20

DNS: ✅ синхронизирован

[ 📄 Открыть домен ]
[ 🏠 Главное меню ]
```

При ошибке provider бот не должен писать секретные технические подробности.

Пример:

```text
⚠️ Не удалось завершить настройку DNS.
Операция сохранена с ошибкой и доступна в истории.

Код: dns_provider_unavailable
```


## Добавление записи

```text
Выберите тип:

[ A ] [ AAAA ] [ CNAME ]
[ TXT ] [ MX ] [ NS ]

[ ← Назад ]
```

Далее бот запрашивает только поля, необходимые выбранному типу.

Например MX:

```text
Имя → сервер → priority → TTL → подтверждение
```

# Карточка сервера

```text
🖥 Hermes

Статус: 🟢 Online
IPv4: 203.0.113.20
Окружение: production
Домены: 7

[ 🌐 Домены ]
[ ➕ Привязать домен ]
[ ✏️ Изменить ]
[ 📜 История ]

[ ← Серверы ]
```

В первой версии `Online` не должен обещать глубокий мониторинг. Нужно явно определить источник статуса: ручной, DNS/ICMP/TCP-check или неизвестен.

# Удаление домена

Destructive flow всегда с явным подтверждением.

```text
⚠️ Удалить panel.bakunity.online?

Будут удалены управляемые DNS-записи, связанные с этим ресурсом.

Это действие может повлиять на доступность сервиса.

[ 🗑 Да, удалить ]
[ Отмена ]
```

Для особо критичных операций позже можно добавить дополнительное подтверждение текстом.

# Административный раздел

Пример:

```text
⚙️ Управление

[ 🌍 DNS-зоны ]
[ 👥 Пользователи ]
[ 🖥 Все серверы ]
[ 📜 Аудит ]
[ 🔐 Роли и права ]
[ ⚙️ Настройки ]
```

В первой версии административные сценарии можно реализовать частично в Web, если в Telegram они становятся слишком длинными.

# Состояния и навигация

Бот должен:

- сохранять состояние многошагового сценария;
- позволять отменить действие;
- корректно переживать устаревшую кнопку;
- не выполнять повторно mutation из старого callback;
- использовать короткие callback payload и внутренние IDs;
- проверять права заново на финальном действии;
- не считать показанную кнопку доказательством права.

# Редактирование одного сообщения

Где это улучшает UX, предпочтительно обновлять текущее сообщение вместо отправки длинной цепочки новых сообщений.

Но важные результаты mutation и ошибки можно отправлять отдельным сообщением, если это делает историю понятнее.

# Telegram-first, но не Telegram-only

Новая возможность не должна проектироваться так, будто Telegram — единственный клиент.

Правильная последовательность:

```text
Use case
   ↓
Backend правила
   ↓
Telegram UX
   +
Web UX
```

Telegram может получать интерфейс раньше, но не отдельную версию бизнес-правил.
