# Web UX

Веб-панель — основной полнофункциональный клиент Bakunity Infra. Она использует те же application use case и права, что и Telegram, но лучше подходит для работы с большим количеством ресурсов, таблицами, фильтрами, аудитом и настройками.

Предполагаемый адрес в будущем:

```text
infra.bakunity.online
```

Адрес не является жёстким архитектурным требованием и может измениться.

# Основные принципы

- Web не содержит самостоятельных DNS-правил.
- Все mutation проходят через backend.
- UI скрывает недоступные действия, но backend всё равно проверяет права.
- Один и тот же ресурс имеет одинаковое состояние в Web и Telegram.
- Опасные действия требуют явного подтверждения.
- Provider-specific детали показываются только там, где это действительно полезно.

# Вход и сессия

Web authentication V1 зафиксирован в `ADR-0010`: основной способ входа — **Passkey/WebAuthn**.

Базовый login flow:

```text
Открыть Web Console
      ↓
[ Войти с passkey ]
      ↓
браузер запускает WebAuthn ceremony
      ↓
backend проверяет assertion
      ↓
создаётся server-side session
      ↓
GET /api/v1/me
      ↓
Dashboard
```

Web не хранит роли/permissions или долгоживущий bearer token в `localStorage` как источник доверия. Browser session представлена opaque `Secure` + `HttpOnly` cookie.

Если session истекла или отозвана, пользователь возвращается на экран входа без потери server-side project state.

Минимальные состояния экрана входа:

- ready;
- passkey prompt active;
- authentication cancelled;
- credential not recognized;
- user blocked/disabled;
- temporary backend error.

Публичная самостоятельная регистрация по умолчанию не входит в V1. Добавление нового passkey выполняется через контролируемый bootstrap/invite либо из уже аутентифицированного профиля.

В профиле пользователя позже должен быть раздел «Passkeys», где можно:

- посмотреть зарегистрированные credentials по безопасной metadata;
- добавить новый passkey;
- отозвать credential;
- завершить другие Web sessions;
- завершить текущую session.

Удаление последнего credential должно иметь отдельную защиту от потери доступа.

Telegram linking остаётся отдельным действием: Telegram не является обязательным Web login provider.

# Общая навигация

```text
Bakunity Infra
├── Обзор
├── Домены
├── DNS-зоны
├── Серверы
├── Деплои          ← позже
├── Мониторинг      ← позже
├── Аудит
├── Пользователи    ← по правам
└── Настройки       ← по правам
```

На раннем этапе пункты будущих модулей не должны имитировать готовый функционал. Их лучше не показывать до появления реальной реализации.

# Dashboard

Главная страница отвечает на вопрос: «Что сейчас есть в моей инфраструктуре и есть ли проблемы с управляемым состоянием?»

Пример:

```text
┌──────────────────────────────────────────────────┐
│ Bakunity Infra                         Профиль    │
├───────────────┬──────────────────────────────────┤
│ Обзор         │ Домены              12           │
│ Домены        │ Серверы              4           │
│ DNS-зоны      │ Ошибки DNS           1           │
│ Серверы       │ Последние действия   8           │
│ Аудит         │                                  │
│ Настройки     │ [ + Создать поддомен ]           │
└───────────────┴──────────────────────────────────┘
```

Полезные блоки первой версии:

- количество доменов;
- количество доступных зон;
- количество зарегистрированных серверов;
- ошибки синхронизации DNS;
- последние действия;
- быстрый переход к созданию поддомена.

Dashboard V1 не должен показывать «серверы online», пока Monitoring/reachability официально не реализован.

# Создание поддомена

Лучше использовать короткую форму или wizard без лишних экранов.

```text
Создать поддомен

Зона
[ bakunity.online ▼ ]

Имя
[ panel              ]

Назначение
(●) Сервер
( ) IPv4
( ) CNAME

Сервер
[ Hermes ▼ ]

                  [ Отмена ] [ Создать ]
```

До отправки формы UI может выполнять удобную локальную валидацию, но окончательное решение принимает backend.

После успешного создания пользователь попадает на карточку домена.

# DNS-зоны

Обычный пользователь видит только зоны, в которых ему разрешено создавать или просматривать ресурсы.

Администратор видит расширенную карточку:

```text
bakunity.online
Provider: Cloudflare
Status: Active
Поддоменов: 21
Публичная выдача: Да/Нет
Лимит на пользователя: 3
```

Подключение нового provider/token относится к административной настройке и должно быть отделено от обычного DNS-управления.

Zone-level/apex/system DNS records относятся к административной области. Обычный пользователь работает с records через принадлежащий ему Domain Resource.

# Серверы

## Список

```text
Имя       IPv4             Окружение    Регион    Домены   Состояние
Hermes    203.0.113.20     production   EU        7        Active
Stage-1   203.0.113.30     staging      EU        3        Active
Old-1     203.0.113.40     staging      EU        0        Disabled
```

Фильтры:

- environment;
- registration status;
- provider;
- region;
- label.

`Active/Disabled` — состояние server resource внутри Bakunity Infra, а не результат health check.

# Карточка сервера

Показывает:

- имя;
- IP;
- environment;
- provider/region;
- labels;
- registration status;
- список привязанных доменов;
- audit history;
- reachability: «не настроена», пока нет отдельной проверки.

На этапе каталога серверов не нужно создавать иллюзию, будто система уже управляет ОС сервера или знает его реальную сетевую доступность.

# Аудит

Полноценный Web-интерфейс для поиска событий:

```text
Дата/время
Пользователь
Клиент
Действие
Ресурс
Результат
```

Фильтры:

- период;
- пользователь;
- source client;
- action;
- resource type;
- status/result.

Карточка события показывает безопасные metadata и request/correlation ID, но не секреты.

# Пользователи и права

Доступен только соответствующим ролям.

Список пользователей:

```text
Пользователь    Статус    Telegram    Web    Роль
Timas           active    linked      yes    Admin
User 12         active    linked      yes    Member
```

Карточка пользователя:

- identities;
- passkeys (без sensitive credential material);
- активные/отзываемые Web sessions, если разрешено;
- роли;
- эффективные права;
- лимиты;
- принадлежащие домены;
- последние audit events.

Изменение прав, credential lifecycle и административный session revoke должны создавать audit/security event там, где это уместно.

# Ошибки и состояния

Нужно различать:

- loading;
- empty state;
- validation error;
- permission denied;
- provider error;
- partial/unknown synchronization state;
- resource deleted/disabled.

Не использовать абстрактное «Что-то пошло не так» там, где backend вернул стабильный безопасный error code.

Пример:

```text
Не удалось синхронизировать DNS-запись.
DNS-провайдер временно недоступен.

Код операции: req_...
[ Повторить ]
```

# Realtime и обновления

Для первой версии не требуется сложный realtime.

Достаточно:

- обновления после mutation;
- ручного refresh;
- polling только там, где операция действительно асинхронная.

WebSocket/SSE добавляются при реальной необходимости.

# Responsive

Web-панель должна оставаться usable на мобильном устройстве, но Telegram остаётся более удобным быстрым мобильным клиентом.

На маленьком экране:

- таблицы переходят в карточки или горизонтальный scroll;
- критичные действия не прячутся в труднодоступные области;
- подтверждения destructive actions остаются явными.

# Визуальный приоритет

Интерфейс должен быть утилитарным и чистым. Основной фокус — состояние инфраструктуры и действия, а не декоративные dashboard-блоки.

Приоритет отображения:

```text
1. Ресурс
2. Его управляемое состояние
3. Куда он направлен / с чем связан
4. Доступные действия
5. История и технические детали
```

# Связь с Telegram UX

Web и Telegram могут выглядеть совершенно по-разному, но используют одинаковые понятия:

```text
Zone
Domain
DNS Record
Server
Binding
Audit Event
```

Если в одном клиенте появляется новое бизнес-состояние, оно должно быть определено в доменной модели, а не существовать только в UI.
