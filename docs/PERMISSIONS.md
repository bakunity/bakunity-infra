# Роли и права доступа

Bakunity Infra управляет инфраструктурными ресурсами, поэтому контроль доступа должен быть частью backend-логики с первой версии.

## Базовый подход

Используем комбинацию:

- **RBAC** — роль даёт набор разрешений;
- **ownership** — пользователь может иметь права только на собственные ресурсы;
- **scoped access** — позже роль можно ограничить конкретной зоной, сервером или проектом.

Наличие кнопки в Telegram или Web не является проверкой прав.

```text
Клиент
   │
   ▼
Authentication
   │
   ▼
Internal User
   │
   ▼
Authorization
   │
   ▼
Use case
```

# Системные роли первой версии

## Superadmin

Полный системный доступ.

Используется владельцем платформы и минимальным количеством доверенных администраторов.

Может:

- управлять пользователями и ролями;
- подключать DNS-провайдеры;
- управлять всеми DNS-зонами;
- видеть все домены;
- управлять всеми серверами;
- менять системные лимиты;
- видеть полный audit log;
- выполнять административные операции.

## Admin

Администратор инфраструктуры без обязательного доступа к самым чувствительным platform settings.

Может:

- управлять доступными зонами;
- видеть и управлять доменами пользователей в разрешённой области;
- управлять серверным каталогом;
- просматривать аудит;
- управлять частью пользовательских прав, если это явно разрешено.

## Operator

Операционная роль.

Может выполнять повседневные инфраструктурные действия, но не менять модель доступа или provider credentials.

Примеры:

- создавать и изменять домены;
- управлять DNS-записями;
- привязывать домены к серверам;
- просматривать серверы;
- просматривать операционный аудит.

## Member

Обычный пользователь платформы.

По умолчанию работает только со своими ресурсами и в разрешённых DNS-зонах.

Может:

- создавать поддомены в доступных зонах;
- видеть свои домены;
- управлять разрешёнными DNS-записями своих доменов;
- использовать доступные ему серверы как target, если политика это разрешает;
- видеть свою историю действий.

## Viewer

Роль только для чтения.

Может видеть разрешённые ресурсы, но не выполнять mutation.

# Permission codes

Предварительный набор разрешений.

## Домены

```text
domains.read
domains.read_all
domains.create
domains.update
domains.delete
domains.transfer_ownership
```

## DNS

```text
dns.records.read
dns.records.create
dns.records.update
dns.records.delete
dns.zones.read
dns.zones.manage
dns.providers.manage
```

## Серверы

```text
servers.read
servers.read_all
servers.create
servers.update
servers.delete
servers.bind_domain
```

## Пользователи и доступ

```text
users.read
users.manage
roles.read
roles.manage
limits.manage
```

## Аудит

```text
audit.read_own
audit.read_all
```

## Будущие модули

```text
deployments.read
deployments.create
deployments.rollback
proxy.manage
certificates.manage
monitoring.read
```

Эти права не нужно реализовывать раньше соответствующих модулей.

# Матрица ролей первой версии

Условная стартовая матрица:

| Возможность | Superadmin | Admin | Operator | Member | Viewer |
|---|---:|---:|---:|---:|---:|
| Видеть свои домены | ✅ | ✅ | ✅ | ✅ | ✅ |
| Видеть все домены | ✅ | ✅ | ✅* | ❌ | ❌ |
| Создавать поддомен | ✅ | ✅ | ✅ | ✅ | ❌ |
| Менять свои DNS-записи | ✅ | ✅ | ✅ | ✅ | ❌ |
| Менять чужие DNS-записи | ✅ | ✅ | ✅* | ❌ | ❌ |
| Управлять DNS-зонами | ✅ | ✅* | ❌ | ❌ | ❌ |
| Управлять provider credentials | ✅ | ❌* | ❌ | ❌ | ❌ |
| Видеть серверный каталог | ✅ | ✅ | ✅ | по политике | по политике |
| Добавлять/удалять серверы | ✅ | ✅ | ❌* | ❌ | ❌ |
| Привязывать домен к серверу | ✅ | ✅ | ✅ | по политике | ❌ |
| Видеть полный аудит | ✅ | ✅ | ✅* | ❌ | ❌ |
| Видеть собственный аудит | ✅ | ✅ | ✅ | ✅ | ✅ |
| Управлять пользователями | ✅ | ✅* | ❌ | ❌ | ❌ |
| Управлять ролями | ✅ | ограниченно* | ❌ | ❌ | ❌ |

`*` — точная область определяется scope/policy и должна быть зафиксирована перед реализацией конкретного endpoint.

# Ownership

У доменного ресурса есть `owner_user_id`.

Обычное правило:

```text
Member + domains.update
+
resource.owner_user_id == current_user.id
→ разрешено
```

Если у пользователя есть `domains.read_all` или административное scoped permission, проверка ownership может быть расширена.

# Доступ к DNS-зонам

Не каждая зона обязана быть доступна каждому пользователю.

Варианты политики зоны:

```text
private       — только администраторы/явно разрешённые пользователи
members       — доступна обычным пользователям
restricted    — доступ по отдельному scope/списку
```

Точная модель хранения может быть уточнена при проектировании persistence.

# Доступ к серверам

Серверный каталог может содержать внутренние узлы, которые нельзя показывать всем пользователям.

Поэтому отдельно различаем:

- право видеть server resource;
- право использовать его как target;
- право изменять metadata;
- право управлять сервером удалённо в будущих версиях.

Доступ к серверу не должен автоматически означать SSH-доступ.

# Telegram и Web

Один пользователь может иметь две identity:

```text
User #1
├── Telegram
└── Web
```

Эффективные права одинаковы независимо от клиента.

Нельзя делать:

```text
Telegram admin list
отдельно от
Web roles
```

как две независимые системы прав.

Допускается отдельное ограничение действия по типу клиента только если есть реальная security-причина и оно явно описано политикой.

# Проверка прав

Authorization выполняется как минимум:

1. при открытии/чтении чувствительного ресурса;
2. перед каждым mutation use case;
3. повторно на финальном шаге многошагового Telegram flow;
4. при выполнении фоновой операции, если она использует сохранённый user context.

# Изменение ролей

Изменение роли или прав — значимое административное действие.

Оно должно:

- требовать отдельного permission;
- попадать в audit log;
- фиксировать actor;
- фиксировать старое и новое безопасное состояние;
- не позволять обычному Admin повысить себя до Superadmin, если это не разрешено политикой.

# Блокировка пользователя

`blocked` пользователь:

- не может создавать mutation;
- не должен получать новые session/token;
- Telegram-команды должны завершаться безопасным сообщением об отсутствии доступа;
- уже запущенные чувствительные операции должны учитывать текущую политику, если это технически возможно.

# Принцип минимальных прав

По умолчанию новое действие запрещено, пока оно явно не разрешено ролью/permission.

Особенно это относится к будущим возможностям:

- SSH;
- deployment;
- reverse proxy;
- TLS;
- secret management;
- server agent commands.

# Что фиксируем до разработки

На старте считаем базовыми роли:

```text
superadmin
admin
operator
member
viewer
```

и строим backend вокруг permission checks, а не вокруг `if role == ...` в каждом handler.

При реализации конкретные permission names можно уточнить, но общая модель RBAC + ownership + scope должна сохраниться.
